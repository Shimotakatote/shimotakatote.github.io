Automating my own job

The problem

A lot of my week was admin. Every morning I checked my sprint board, my email and the support inbox to work out what needed me. At the end of a task I wrote a handoff and moved the card. At the end of the day I logged my time by hand. On Fridays I wrote a status update. Every so often I counted my finished tasks for a quarterly goal.

None of it was hard. All of it was repeated, and all of it pulled from systems I already had access to. Most of these skills started the same way: I did the task by hand once, then wrote it down so Claude Code could do it next time.

What I built

Five skills. Each one is a written procedure plus small Python scripts that Claude Code follows.

Morning sprint check. It pulls my open sprint tasks from Asana, with every comment posted since the last workday. Then it checks Gmail and Intercom for anything tied to those tasks. I get one short report, sorted into: do now, nudge someone, ready to close, in the wrong stage, waiting, and anything new outside the sprint.

Session wrap-up. A checkpoint for work that continues later. It checks the live facts, logs my time, moves the task to the right stage (Waiting, Validating, Review or Building), drafts a handoff comment, lists open loops with an owner for each, sets the next check-in, cleans up local leftovers and updates its notes.

Daily time log. It measures how long I actually worked on each task from my Claude Code session transcripts, then posts the time to Asana. The steps are below.

Friday status. It pulls what shipped, closed and moved since the last update, checks each claim against Asana, picks On track, At risk or Off track, and posts the weekly status for my project.

Quarterly goal update. It counts the sprint tasks I completed this quarter and last quarter, sets the goal's current value and reads it back. It sets the value only. It never posts a status on the goal.

How the time log works

  1. Read the transcripts

    Every Claude Code session leaves a transcript with timestamps. The script reads the day's sessions.

  2. Measure active time

    Any gap longer than 15 minutes is capped, so lunch or a break is not billed.

  3. Split parallel sessions

    I often ran parallel sessions, one per task. When they overlap, the minutes are split between them, so a day never adds up to more than the clock.

  4. Match each session to a task

    Each session is matched to the Asana task it worked on. Only clear matches get posted.

  5. Check the ledger, post, read back

    The time log and the session wrap-up share one ledger. A session that is already in it is skipped, so nothing is logged twice. After posting, the script reads the entry back from Asana.

The safety rules

These skills touched shared systems, so they followed three rules.

  1. Read-only by default. The morning check only reads and drafts. The session wrap-up asks before each write. The scheduled skills each have one narrow write and nothing else.
  2. Drafts only. Messages to people are drafted, not sent. The Friday status post is the one message that goes out on its own. The time log and the goal update write only time entries and one number.
  3. Read back every write. After a skill writes something, it reads it back from the system to prove it landed.

The scripts use the Python standard library only, so there is nothing to install. Some Asana calls run as in-page requests through Claude in Chrome.

What changed

Between 2 October and 13 November 2026, the time log and the wrap-up posted 6,133 minutes to Asana in 77 entries. That is about 102 hours I did not have to type in or remember.

The bigger change was the morning. Instead of checking Asana, Gmail and Intercom one by one, I read one report and started on the first item.
