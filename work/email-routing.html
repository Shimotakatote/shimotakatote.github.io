05IT services · Email → Intercom

Email routing cleanup

Automated alerts were landing on people, and almost all of them were being cleared by hand.

Stack
Intercom workflows and API, Python analysis scripts, Claude Code scheduled tasks
Role
I did the analysis, designed the rules and set up the check after go-live.
Status
Rules live since Nov 2026, still in validation
Numbers
  • 591 of 634 alerts had been cleared by hand
  • 99 → 37 emails reaching people, same sample
  • 51 real emails saved from a bad rule
  • 14/14 alerts routed right after go-live

The problem

The support inbox in Intercom took in email from everywhere. Some of it came from customers. A lot of it came from machines: script alerts, security alerts, backup reports and marketing.

The automated mail landed on the help desk, the same as a customer email. Someone had to open it, see it was an alert, and clear it. Then do it again for the next one.

Alerts from our Apps Script automations were the clearest case. Since 17 September, 634 of them had reached people. 591 had been marked as spam by hand.

591 / 634Apps Script alerts cleared by hand

The whole bar is 634 alerts. The dark part is the 591 cleared by hand.

These alerts were not junk. They just went to the wrong people. Script alerts belonged with engineering. Security and backup alerts belonged with the service desk.

What I built

I shipped a few narrow rules instead of one big one, and tested each on real traffic before it touched a live email.

  • A simulation first. I pulled a 4-day sample of real inbound email and wrote Python scripts that run a routing rule over it. That shows what each rule would catch before it goes live.
  • One rule rejected. The obvious fix was a blanket rule: anything from a no-reply address goes to spam. The simulation showed it would have spam-tagged 51 real emails. I dropped it.
  • Narrow rules shipped. Exact-sender branches in Intercom workflows. Apps Script alerts go to engineering. Security and backup alerts go to the service desk. Marketing goes to spam.
  • A check that only reads. An hourly scheduled task looks at where alerts ended up and reports it. It never changes anything.

How it works

  1. Take a real sample

    I pulled 4 days of real inbound email from Intercom. Real traffic shows the senders you forgot about.

  2. Simulate each rule

    A Python script runs a candidate rule over the sample. It counts what would move and lists every email the rule would catch, so I can read them.

  3. Throw out the risky ones

    Any rule that catches real emails does not ship. The no-reply rule caught 51, so it went.

  4. Ship exact senders only

    The rules that went live match exact senders. A new alert sender is not caught by accident. It stays visible until someone adds it on purpose.

  5. Watch it after go-live

    The hourly read-only check confirms each watched alert lands in the right place. After go-live, 14 of 14 did.

What changed

I replayed the same 4-day sample through the new rules. Emails reaching people went from 99 to 37.

Some alerts still reach people. I could have pushed the 37 lower with a wider rule. But a wider rule is how you get the 51. A missed alert costs someone a click. A hidden customer email costs a lot more.

The part I would reuse is the order: sample, simulate, read what the rule catches, then ship. It took longer than writing one rule. It also meant I knew what would happen before go-live.
