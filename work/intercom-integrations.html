04IT services · Intercom → WHMCS, Asana

Intercom integration suite

A billing sidebar and an Asana sidebar inside Intercom, plus a service that adds each contact's email domain.

Stack
Node.js, Express, Intercom Canvas Kit, API and webhooks, WHMCS API, PHP, Asana API, Google Cloud Run, Docker, VPC egress, Cloud NAT
Role
I built all three pieces, from the API work to the deploy.
Status
Billing sidebar live since Feb 2026. I maintained the suite to Sep 2026.
Numbers
  • 10 people on the support team, no tab-switching
  • Near zero running cost on Cloud Run
  • 3 services
  • 5 webhook event types handled

The problem

The support team worked out of Intercom. Most of the answers they needed did not. Billing lived in WHMCS. Project work lived in Asana.

So a simple billing question went like this. Copy the customer's email. Open WHMCS in another tab. Search. Find the right client. Read the invoice. Go back to the conversation and reply. A "where is my job up to?" question meant the same trip, this time to Asana.

Intercom contacts also had no domain field. If you wanted to route or report by company, there was nothing to filter on.

What I built

Three small services. Each one puts data into a tool the team already had open.

  • Billing sidebar. An Intercom inbox app. Open a conversation and the right-hand panel shows that customer's WHMCS record: client info, active subscriptions, invoices, notes and tickets.
  • Asana sidebar. The same idea, for Asana. It searches by the contact's name, domain and email. It shows a badge with the number of matching tasks, then the client's projects and quick links.
  • Domain service. A webhook service that writes each contact's email domain into a custom "Domain" attribute on the contact.

How it works

The billing sidebar is the busiest of the three, so here is what happens when an agent opens a conversation.

  1. Intercom calls the app

    Intercom sends the contact's details to the service on Cloud Run. The service checks the HMAC signature first and drops any request that does not match.

  2. Find the customer

    It looks up the WHMCS client by the contact's email address.

  3. Fetch it all at once

    Client info, subscriptions, invoices, notes and tickets are requested in parallel, not one after another. The panel waits for the slowest request, not for all of them in a row.

  4. Fill the gaps in the API

    A few WHMCS API endpoints did not return what the panel needed. I wrote small custom PHP API modules on the WHMCS side to return it.

  5. Draw the panel

    The answer goes back as Canvas Kit components, so it renders inside Intercom's own panel and looks like part of the inbox.

One more detail. A Cloud Run service does not get a fixed outbound address by default. I sent its traffic through VPC egress and Cloud NAT, so every call to WHMCS comes from one static IP.

The Asana sidebar follows the same pattern. It asks Asana instead of WHMCS.

The domain service

This one has no screen of its own. It listens for five Intercom webhook event types. When one arrives for a contact, it takes the part of the email after the @ and writes it to the Domain attribute.

That only covers contacts from then on. For the ones that already existed, I wrote a backfill. It pages through the contacts and is rate-limited, so it stays inside Intercom's API limits while it runs. Both paths check the HMAC signature before they write anything.

What changed

10people on the support team stopped switching tabs
Near zerorunning cost on Cloud Run

The 10-person support team no longer leaves Intercom to check billing or find a task. The answer sits next to the conversation they are already in.

The services run on Cloud Run, which scales to zero when nobody is using them. That keeps the running cost near zero.

The Domain attribute made something possible that was not possible before: routing and reporting by company domain.

Each service does one job inside a tool the team already used.
